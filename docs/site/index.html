02 / DECISION LOGIC

A signal needs context.

Provider disagreement is visible. IPinfo adds network context; AbuseIPDB and VirusTotal determine reputation coverage. A classification is neither incident severity nor a probability of compromise.

ILLUSTRATIVE FIXTURES · NO API CALLS
ASSESSMENT / RULES 2.0

conflicting_evidence

VirusTotal has one flag while AbuseIPDB is available with zero confidence. The disagreement needs investigation; it does not establish maliciousness.

Human decision required. Correlate evidence with the observed activity.
Read the ordered classification rules
  1. Elevated abuse confidence (≥50 with reports) + vendor flags → cross_source_signals
  2. Elevated abuse confidence with reports → abuse_signal
  3. Exactly one flag + available zero-confidence AbuseIPDB → conflicting_evidence
  4. One flag → isolated_signal
  5. Multiple flags → multiple_vendor_signals
  6. Pending jobs → pending
  7. Incomplete reputation coverage → inconclusive
  8. Relevant underlying observation older than 30 days → outdated_evidence
  9. Otherwise → no_known_malicious_evidence

Earlier rules take precedence. Positive signals can remain classified with stale or partial quality warnings. A cached retrieval timestamp is not the observation timestamp.

03 / CASE RECORD

Preserve the reasoning.

The final output is an investigation record, not just a score. Reopening a case can show both new evidence and the conclusion an earlier review referenced.

01

Evidence

Provider status, normalized findings, retrieval and observation dates, HTTP status and cache provenance.

02

Assessment

A saved snapshot binds the evidence to its conclusion and rule version. Unchanged evidence reuses a snapshot.

03

Review

An authenticated reviewer records an explanation and disposition against the latest saved assessment.

Private schema / eight purpose-specific tables
TableResponsibility
providersBudgets, enablement, cooldown and scheduling state
casesIP, reason, request key, assignment and status
jobsProvider work, attempts, eligibility, lease and claim token
case_sources / cacheCase evidence and reusable normalized provider results
assessmentsEvidence snapshots, rules and saved conclusion
reviews / auditAttributed analyst decisions and case events

Closure requires a saved assessment, a final disposition and an explanation of at least three characters. under_review cannot close a case. Final dispositions: confirmed malicious, confirmed benign, insufficient evidence or duplicate. Assignment is separate from reviewer identity.

04 / RESOURCE DISCIPLINE

Bound the work.
Recover deliberately.

The current configuration is intentionally conservative. It protects API allowances and makes failure behavior inspectable; it is not a throughput benchmark.

Growing backlogCheck quota, cooldown and worker health before increasing concurrency.

The scheduled worker processes one eligible job per minute. A case needs multiple provider jobs; cache hits reduce requests. Admission is bounded to 200 case submissions in a rolling day. Review queue age and failed executions daily.

Retention and restoration

Current maintenance removes closed cases last updated more than 90 days ago and removes expired cache older than seven days. Case deletion can cascade to related history. Back up Supabase, n8n configuration and the n8n encryption key through a protected process. Restore permissions and credential bindings before enabling schedules. Backup restoration is a planned assurance exercise.

05 / TRUST MODEL

Trust is explicit.

The backend key stays in n8n. The portal requires an authenticated user. The database limits which client roles can invoke its privileged API.

BROWSER / AUTHENTICATED OPERATOR
n8n portal → trusted server → Supabase service-role RPC
SERVER-SIDE CREDENTIAL BOUNDARY

Implemented

  • Private schema with RLS and no anonymous policies.
  • Backend RPC restricted to service_role, with an empty search path.
  • Original n8n user attribution; typed actor fields discarded.
  • Escaped report content, input validation and bounded provider work.
  • Update protection for assessments and reviews.

Practical limits

  • A privileged backend caller is trusted to supply identity.
  • No independent penetration test or per-case tenant model.
  • MD5 fingerprints deduplicate; they do not prove integrity.
  • Retention and administrators can delete history.
  • No automatic blocking or incident-severity inference.

Rotate keys shared in chat. Keep credentials, encryption keys and backups out of Git. Execution history contains investigation data: configure its access and retention. The repository export removes credential bindings and imports inactive.

06 / REPRODUCIBILITY

From export to workspace.

Use the sanitized workflow and versioned SQL as a portable reference. The existing production instance needs no change to read this documentation.

  1. 01

    Prepare the backend

    Create a Supabase project. For a fresh project, apply the local migrations in filename order. For the existing deployment, compare its migration ledger first: the local baseline consolidates historical fixes. Do not blindly push it over a running database.

  2. 02

    Import the workflow inactive

    Import workflows/ip-intelligence-unified.sanitized.json in a compatible n8n version. Set the Supabase URL in System configuration. Review form access and regeneration of webhook identifiers.

  3. 03

    Bind four stored credentials

    Supabase backend API key, AbuseIPDB Key header, VirusTotal API credential and IPinfo Lite Bearer auth. Use the credential types and request format in the setup guide. Never put a backend secret in a public frontend.

  4. 04

    Verify, then activate

    Inspect metrics, submit one public IP, wait for worker ticks, retrieve the report and record an explained review as an authenticated user. Check partial-failure behavior and anonymous rejection. Use the production form URL after activation.

07 / ENGINEERING EVIDENCE

Show what was tested.
Name what remains.

The repository includes dated acceptance records and transactional SQL suites. Recorded checks cover successful paths and controlled failure behavior.

REAL PROVIDERS

Public-IP enrichment, asynchronous queue processing, cache reuse, duplicate submission and report retrieval.

PINNED RESPONSES

Rate limits, failed authentication, timeouts, missing records and malformed evidence. Analyst identity was simulated in the latest workflow tests.

TRANSACTIONAL SQL

Budget resets, claim fencing, lease recovery, attempts, snapshot preservation and review constraints. Test fixtures roll back.

NOT ESTABLISHED

Production throughput, an independent security audit, disaster recovery or a fresh browser sign-in in the latest analyst test run.

NEXT / PLANNED, NOT IMPLEMENTED

Queue latency and restoration checks → structured event context and access controls → authenticated idempotent ingestion → filtered Wazuh alerts. Avoid enriching every alert without admission control.
